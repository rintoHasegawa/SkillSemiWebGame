# 時刻同期・ラグ対策 (Clock Synchronization & Lag Mitigation)

## 概要 (Overview)

### 目的 (Purpose)

通信遅延が存在する環境で，全クライアントとサーバーが同じゲーム内時刻を共有し，
ボムの爆発タイミングなどの時間依存イベントを全端末で同時に発生させる．

### 主要な手法 (Key Techniques)

- サーバーのゲーム時計: 単調時計1本で試合の経過時間を管理し，壁時計に依存しない
- Ping/Pongクロック同期: 4タイムスタンプでRTTとゲーム経過時間へのオフセットを推定する
- 最小RTTサンプル採用: 直近サンプル窓のうちRTTが最小のものを推定値に採る
- slew追従: 推定値へ緩やかに寄せ，時計の不連続を防ぐ
- 適応的同期間隔: ネットワーク品質に応じて同期頻度を自動調整する
- ボムの爆発時刻指定: 経過時間ベースでラグに依存しない爆発判定を行う
- クライアントサイド予測: ボム設置をローカルで即座に反映する
- ティックキャッチアップ: サーバー遅延時の連続ティック処理と暴走防止

## サーバーのゲーム時計 (Server Game Clock)

### 単一の時間軸 (Single Time Axis)

ゲーム進行に関わる時刻は，すべて`GameClock`が提供する単調時計の経過時間で表す．壁時計（`Date.now()`）はゲームロジックにも通信ペイロードにも使用しない．

壁時計はNTP補正・仮想マシンのサスペンド・利用者による時刻変更のいずれでも不連続に飛ぶ．ゲーム進行がそれを読むと，爆弾が永久に回収されないなどの破綻を招く．

- `GameRoomSession`が`GameClock`を1つ生成し，`GameLoop`と共有する（1インスタンス・2リーダー）
- 原点は`start()`の呼び出し時点で確定する
- 開始待機（カウントダウン）は，初回ティックを`原点 + GAME_START_DELAY_MS + TICK_RATE`に置くことで吸収する
- カウントダウン中はティックが1度も回らない

原点を「`setTimeout`が実発火した時刻」ではなく「`start()`を呼んだ時刻」に置くことで，待機処理のドリフトが時間軸に混入しない．

### 提供する値 (Provided Values)

| メソッド | 意味 |
| --- | --- |
| `getRawElapsedMs()` | 原点からの経過ms（ティックのスケジュールに使う） |
| `getElapsedMs()` | ゲームプレイ開始からの経過ms（カウントダウン中・未開始時は0） |
| `getSignedElapsedMs()` | ゲームプレイ開始からの経過ms（カウントダウン中は負値） |
| `hasGameplayStarted()` | ゲームプレイが開始済みか |

ワイヤに載るのは`getSignedElapsedMs()`のみである．カウントダウン中の負値を含めて送ることで，クライアントは開始前カウントダウンと開始後の経過を同一の値として扱える．

### 待機時間の一元管理 (Single Source of Start Delay)

開始待機時間は`GameClock`のみが保持し，`GameLoop`は`getStartDelayMs()`で読む．両者が別々に値を持つと「カウントダウン中にティックが回る」「終了判定だけずれる」という検知しづらい不整合が起きるため，構造的に食い違わない形にしている．

## Ping/Pongクロック同期 (Clock Synchronization)

### プロトコル (Protocol)

1. クライアントが`PING`イベントで自身の単調時計の値（`clientTime`）を送信する
2. サーバーが`PONG`イベントで`clientTime`と，PING受信時・PONG送信時の2点のゲーム経過msを返す
3. クライアントが`PONG`受信時刻からRTTとオフセットを算出する

セッションが開始していない場合（ロビー中など）はゲーム時間軸が存在しないため，サーバーは`PONG`を返さない．

### RTT・オフセット算出 (RTT and Offset Calculation)

4つのタイムスタンプを用いる．`t0` = `clientTime`，`t1` = `serverReceivedElapsedMs`，`t2` = `serverSentElapsedMs`，`t3` = `PONG`受信時刻．

- サーバー滞留時間: `serverProcessingMs = t2 - t1`
- RTT計測: `measuredRttMs = (t3 - t0) - serverProcessingMs`
- 片道遅延推定: `estimatedOneWayMs = measuredRttMs / 2`
- オフセット算出: `offsetMs = t2 - (t3 - estimatedOneWayMs)`

サーバーの処理時間をRTTから差し引くため，イベントループの滞留が片道遅延の推定を汚さない．

オフセットは「クライアントの単調時計 → サーバーのゲーム経過ms」への変換値である．`クライアント単調時計 + offsetMs`がサーバーのゲーム経過msの推定値になる．

### 初期オフセットのシード (Initial Offset Seeding)

`GAME_START`受信時に，`PONG`を待たずに`serverElapsedMs`からオフセットの初期値を設定する．

- 算出: `offsetMs` = `serverElapsedMs` - `GAME_START`受信時刻
- この値は片道遅延を補正していないため，真のオフセットより**片道遅延ぶん過小**になる
- シード値はサンプル窓に入れず，**窓が空の間だけ使うフォールバック値**として別に保持する
- 最初の有効サンプルが入った時点で，シード値は使われなくなる

カウントダウン中に`PONG`を数回交換できるため，ゲームプレイ開始時点ではオフセットが収束している．

### RTT外れ値フィルタ (RTT Outlier Filter)

- 負のRTT: 棄却する（サーバー滞留時間が往復を上回る異常値）
- 1000ms超のRTT: 棄却する（ネットワーク異常として無視）
- バリデーション失敗時は`null`を返し，オフセット更新をスキップする

## オフセットの推定と追従 (Offset Estimation & Following)

推定と追従を分離する．推定は「真のオフセットはいくつか」を，追従は「現在値をそこへどう寄せるか」を担う．

### 最小RTTサンプル採用 (Minimum-RTT Sample Selection)

直近8件（`SAMPLE_WINDOW_SIZE`）のサンプルをリングバッファで保持し，**RTTが最小のサンプルのオフセットをそのまま推定値とする**．平均やEWMAは用いない．

ネットワーク遅延のノイズは**片側分布**である．パケットは理論最短時間より速くは到達せず，キューイングで遅れる方向にしか振れない．したがってRTTの分布は右に大きく歪んでおり，オフセットを平均やEWMAで畳み込むと歪んだ裾に引きずられて**系統的なバイアス**が乗る．

RTTが最小のサンプルはキューイング遅延が最も少なく，`片道遅延 = RTT / 2`という対称性の仮定が最も成立している．NTPのclock filterも同じ理由で同じ選び方をする．

古いサンプルは窓から自然に押し出されるため，誤った値に推定が固定されたまま復帰できなくなる状態は構造的に発生しない．

### slewによる追従 (Slew Following)

- 最初の推定値は**slewを経ず即座に採用**する（試合開始時に一気に合わせるため）
- 2件目以降は1サンプルあたり`MAX_SLEW_PER_SAMPLE_MS`（50ms）までしか動かさない

壁時計を排したことで，オフセットが正当に大きく動く状況は存在しない（両端とも単調時計であり，差は機器間のクロックドリフトのみ）．そのためslewの上限は「収束速度」ではなく「異常サンプル1件が与えうる時計の段差」を決める値として働く．

### RTTの平滑化 (RTT Smoothing)

- アルファ値: 0.25（約4サンプル分の移動平均に相当）
- オフセットと異なりEWMAを用いる．適応的同期間隔が知りたいのは「典型的な回線品質」であり「最良ケース」ではないため

## 適応的同期間隔 (Adaptive Sync Interval)

### RTTに応じた同期頻度 (RTT-Based Sync Frequency)

- RTT ≤ 80ms（低遅延）: 5000ms間隔で同期する
- RTT ≤ 180ms（中遅延）: 3000ms間隔で同期する
- RTT > 180ms（高遅延）: 2000ms間隔で同期する
- RTT未取得（初期状態）: 3000ms間隔で同期する

### 可変間隔ループ (Variable Interval Loop)

- `setTimeout`ベースで毎回次の同期間隔を再計算する
- ネットワーク品質の変化にリアルタイムで適応する
- 低遅延環境では同期頻度を下げて不要なトラフィックを削減する

## ボムの爆発時刻指定方式 (Elapsed-Time-Based Bomb Detonation)

### 仕組み (Mechanism)

ボムの爆発タイミングをサーバー時刻ではなく，ゲーム開始からの経過時間で指定する．

#### 設置時の流れ (Placement Flow)

1. クライアントが設置を要求し，ローカルには自身の推定経過時間で楽観的に描画する（「クライアントサイド予測」を参照）
2. **サーバーが爆発予定時刻を決める**．クライアント申告値は採用しない
   - `explodeAtElapsedMs` = `GameClock.getElapsedMs()` + `BOMB_FUSE_MS`（1000ms）
3. サーバーがActiveBombRegistryに登録し，全クライアントにブロードキャストする

#### 爆発判定 (Detonation Check)

- クライアント: 各フレームで`elapsedMs >= explodeAtElapsedMs`ならば爆発状態に遷移する
- サーバー: 各ティックで同条件を判定し，Bot向けの被弾判定を実行する

サーバー側は**生成と回収が同じ`GameClock`を読む**．生成を壁時計・回収をループの単調時計で行うと軸が食い違い，壁時計がステップした際に爆弾が回収範囲外へ飛んで永久に残留する（Botが被弾せず，設置者の`bombHitCount`も加算されない）．

### ラグ耐性 (Lag Tolerance)

- 全端末が同じ「経過時間」で判定するため，個別の通信遅延に影響されない
- サーバーACKを待たずにクライアントが独立して爆発を判定できる
- Ping/Pongクロック同期により経過時間の基準が揃っている
- サーバー・クライアントとも単調時計で動くため，どちらの壁時計がステップしても爆発タイミングは影響を受けない

### ボムの状態遷移 (Bomb State Transitions)

- `armed`（設置中）: 設置〜爆発まで
- `exploded`（爆発中）: 爆発〜250ms後まで（爆発エフェクト表示期間）
- `finished`（完了）: エフェクト終了後，描画から除去する

## ボム重複排除 (Bomb Deduplication)

### 重複排除キー (Deduplication Key)

- 形式: `"ownerPlayerId:requestId"`
- クライアントが生成する`requestId`とソケットIDの組み合わせで一意性を保証する

### TTL管理 (TTL Management)

- 有効期間: `BOMB_FUSE_MS + BOMB_DEDUP_EXTRA_TTL_MS` = 1000 + 1000 = 2000ms
- チェック時に期限切れエントリを自動クリーンアップする
- 同一キーが存在する場合はブロードキャストをスキップする

### 防止する問題 (Prevented Issues)

- パケット再送による重複設置
- 同一ボムの複数回ブロードキャスト
- 爆発後の遅延リクエスト処理

## クライアントサイド予測 (Client-Side Prediction)

### ボム設置の即時反映 (Immediate Bomb Placement)

サーバーの応答を待たずにボムをローカルに描画し，体感遅延を解消する．

#### フェーズ1: 楽観的設置 (Phase 1: Optimistic Placement)

1. BombIdRegistryが一時ID（`temp:requestId`）を発行する
2. 一時IDでボムをBombRepositoryに登録し，即座に描画する
3. サーバーにPlaceBombPayloadを送信する

#### フェーズ2: ACK後の差し替え (Phase 2: Replacement After ACK)

1. サーバーから`BOMB_PLACED_ACK`（`bombId`, `requestId`）を受信する
2. `requestId`から一時IDを逆引きする
3. 一時IDのボムを削除し，正式な`bombId`で再登録する

### 効果 (Effect)

- ボム設置のレスポンスが通信遅延（RTT/2）分だけ早く感じられる
- サーバーが拒否した場合は一時ボムを削除するだけで整合性を保てる

## ティックキャッチアップ (Tick Catch-Up)

### 遅延回復機構 (Delay Recovery Mechanism)

サーバーのティック処理が50msを超えた場合，遅れを回復するために連続ティックを実行する．

#### キャッチアップルール (Catch-Up Rules)

- 1サイクルあたり最大3ティックまで連続処理する
- 3ティック処理後も遅延が残る場合は，次回ティック時刻を現在時刻にリセットする
- これにより「キャッチアップスパイラル」（遅延が蓄積し続ける状態）を防止する

### スケジュール方式 (Scheduling Method)

- `setTimeout`で次回ティックの正確な時刻を計算する
- `setInterval`のドリフト（累積誤差）を回避する
- 各サイクル開始時に`nowMs`を取得し，`nextTickAtMs`との差分で判定する

## マップの競合判定 (Map Contest Resolution)

### 問題 (Problem)

同一セルに複数チームのプレイヤーが同時に存在する場合，どのチームが塗るかが不定になる．

### 解決策 (Solution)

- 各ティックで全プレイヤーのグリッド座標を1パスで収集する
- `cellTeamMap`（`Map<gridIndex, teamId>`）を構築する
- 同一セルに異なるチームIDが検出された場合，`CONTESTED_CELL`（-2）を設定する
- `CONTESTED_CELL`のセルは塗り処理をスキップする

### 効果 (Effect)

- 不公平な陣地獲得を防止する
- 1パスで処理が完了し，計算コストが低い
