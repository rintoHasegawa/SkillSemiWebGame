# ゲーム概要・画面遷移仕様 (Game Overview & Screen Flow)

## ゲーム概要 (Game Overview)

### コンセプト (Concept)

チーム対抗の陣取りペイントバトルゲーム．
複数のプレイヤーがリアルタイムで同じフィールドに参加し，自チームの色でマスを塗りつぶして陣地を広げる．
制限時間内に最も多くの面積を塗ったチームが勝利する．

### 基本仕様 (Basic Specifications)

- ジャンル: チーム対抗リアルタイム陣取りゲーム
- チーム数: 4チーム（赤・青・緑・黄）
- 制限時間: 180秒（3分）
- 勝利条件: 終了時に最も多くのセルを塗ったチームが1位
- 対応プラットフォーム: ブラウザ（PC）・ホーム画面に追加した PWA（スマホ）
- 画面方向: 横画面固定（ランドスケープ）

### ゲームの流れ (Game Flow)

1. プレイヤーがルームに参加する
2. ホストがゲーム設定を行い，ゲームを開始する
3. 制限時間内にフィールドを移動し，ボムを設置して自チームの色でマスを塗る
4. 制限時間終了後，チーム別の塗り面積で順位が決定する

## 画面遷移 (Screen Flow)

### 起動ゲート (Launch Gates)

シーン表示の前段に 2 つのゲートを置く．外側がインストールゲート，内側が横画面ゲートである．

#### インストールゲート (Install Gate)

- スマホ（タッチ操作が主の端末）では，ホーム画面に追加した PWA から起動した場合のみプレイできる
- スマホのブラウザで開いた場合はゲーム画面を一切描画せず，ホーム画面追加の手順のみを全面表示する
- 判定条件
  - スマホ判定: `pointer: coarse`（matchMedia 非対応時は `navigator.maxTouchPoints`）
  - PWA 起動判定: `display-mode: standalone` / `display-mode: fullscreen` / iOS の `navigator.standalone`
- 表示する案内
  - 各手順は「番号＋アイコン＋日英併記テキスト」の 1 行で表示する．アイコンは外部画像を使わずインライン SVG で描画する（共有・ホーム画面に追加・トグル・ブラウザメニュー・アプリ起動 等）
  - iOS Safari: 以下の 4 ステップ
    1. Safari 下部の「共有」（Share）ボタンをタップする
    2. 「ホーム画面に追加」（Add to Home Screen）をタップする
    3. 「Web アプリとして開く」（Open as Web App）がオンであることを確認して「追加」（Add）をタップする（オフのままだとブックマークとして追加され Safari で開いてしまう旨を注記する）
    4. ホーム画面に追加されたアイコンからアプリを起動する
  - iOS の Safari 以外のブラウザ: 「Safari で開いてください」の案内（URL コピー → Safari で開く → 共有 →「ホーム画面に追加」）
  - Android: ブラウザメニュー（⋮）→「ホーム画面に追加」/「アプリをインストール」→「追加」→ アイコンから起動の手順．`beforeinstallprompt` を捕捉できた場合は「ホーム画面に追加」ボタンも表示する
  - 端末種別が不明な場合: ブラウザメニュー →「ホーム画面に追加」→ アイコンから起動の手順
- PC（非タッチ端末）はゲートの対象外とし，従来どおりブラウザでプレイできる
- URL クエリ `?allowBrowser=1` を付けた場合はゲートを解除する（実機ブラウザデバッグ用．[ENV_08_スマホ実機デバッグ手順](../02_ENV/ENV_08_スマホ実機デバッグ手順.md) を参照）

※ iOS にはインストール用の API が無いため手順表示のみとする．Android の `beforeinstallprompt` もブラウザの条件次第で発火しないため，手順文は必ず併記する．

#### 横画面ゲート (Landscape Gate)

- 縦画面（ポートレート）ではゲーム画面を隠し，横向き要求メッセージを表示する

### 画面一覧 (Screen List)

- タイトル画面: ゲームへの入口，プレイヤー名とルームIDを入力して入室する
- ロビー画面: ゲーム開始前の待機画面，参加者一覧とゲーム設定を表示する
- ゲーム画面: メインのゲームプレイ画面，移動とボム設置を行う
- リザルト画面: ゲーム終了後の結果表示画面

※ ゲーム中に接続が切れている間は，ゲーム画面の代わりに「再接続中...」の待機表示を出す（「接続断からの復帰」を参照）．

### 遷移フロー (Transition Flow)

タイトル → ロビー → ゲーム → リザルト → タイトル

#### タイトル → ロビー (Title to Lobby)

- トリガー: プレイヤー名とルームIDを入力し「GAME START」ボタンを押す
- 条件: サーバーから入室許可を受け取った場合に遷移する
- 失敗時: エラーメッセージを表示し，タイトル画面に留まる

#### ロビー → ゲーム (Lobby to Game)

- トリガー: ホストが「ゲームスタート」ボタンを押す
- 条件: サーバーからゲーム開始通知を受信した全員が遷移する

#### ゲーム画面の初期化失敗 (Game Initialization Failure)

ゲーム画面は描画エンジン (Pixi.js) の初期化を非同期で行う．WebGL 非対応・GPU コンテキスト喪失等で初期化に失敗した場合の挙動を以下に定める．

- 画面遷移は行わず，ゲーム画面上に全面のエラー表示を出す
  - 見出し: 「ゲームを開始できませんでした」
  - 本文: ページの再読み込み，または別ブラウザでの再試行を案内する
- 無言で未初期化のまま停止させない（失敗の詳細はブラウザコンソールにも記録する）
- 初期化の結果がゲーム画面の破棄後に届いた場合は，エラー表示を出さずに破棄する

#### ゲーム → リザルト (Game to Result)

- トリガー: 制限時間終了（サーバーからゲーム終了＋結果通知を受信）
- 自動遷移: プレイヤー操作不要で遷移する

#### リザルト → タイトル (Result to Title)

- トリガー: 「タイトルへ戻る」ボタンを押す

#### ルームスコープの検証 (Room Scope Validation)

自分が参加していないルームのイベントで画面が遷移しないよう，クライアントは受信時に所属を照合する．

- ルーム状態の同期（ROOM_UPDATE）は，参加者名簿に自分が含まれ，かつ参加中のルームIDと一致する場合のみ反映する
  - ※ 入室直後は参加中のルームIDが未確定のため，名簿に自分が含まれることのみを条件とする（この初回受信でルームIDが確定する）
- ゲーム開始通知（GAME_START）は，通知のルームIDが参加中のルームIDと一致する場合のみ遷移する．未入室の状態では遷移しない
- 条件を満たさないイベントは画面遷移もマップ設定の変更も行わず破棄する（開発時はコンソールにエラーとして記録する）
- サーバー側でも，ルーム削除時に配信チャンネルの在室ソケットを一括退出させ，削除済みルーム宛の配信が残らないようにする

#### 接続断からの復帰 (Recovery from Disconnection)

Socket.IO の接続が予期せず切れた場合（PWA をバックグラウンドへ送った，回線が一時的に切れた 等）でも，ゲーム中であれば**元の席へ復帰できる**．サーバーは切断されたプレイヤーを即座に Bot へ置き換えたうえで，その席を予約して復帰に備える．

##### プレイヤーの同一性 (Player Identity)

- クライアントはセッショントークン（UUID）を生成して `sessionStorage` に保存し，接続時のハンドシェイクの `auth` に `sessionToken` として毎回提示する
- サーバーはプレイヤーID（`playerId`）を接続ID（`socket.id`）から切り離して管理する．これにより，再接続で接続IDが変わっても切断前と同じプレイヤーIDを維持できる
- セッショントークンはタブ単位で保持する（`sessionStorage` を参照できない環境ではメモリ上に保持する）

##### ゲーム中の切断と復帰 (Disconnection and Resume During a Game)

- サーバーは切断を検知した時点でプレイヤーをルームから退室させ，Bot に置き換える（置き換えに猶予期間は設けていない）
- Bot への置き換えに成功した場合に限り，セッショントークンに紐づけて元の席（ルームID・プレイヤーID・プレイヤー名・チーム）を予約する
- 予約に時間制限は無く，寿命はゲームセッションの寿命と一致する．予約が解放されるのは (1) 試合終了時 (2) 明示的な退室時 の 2 つだけである
- クライアントはゲーム画面で接続が切れた場合，タイトルへは戻さず「再接続中...」を表示して復帰を待つ（Socket.IO が自動で再接続を試みる）
- 再接続できたクライアントは復帰要求（`RESUME_SESSION`）を送る．サーバーは予約を消費し，Bot 制御の解除・ルームへの復席・ルーム配信チャンネルへの再参加・プレイヤーIDの新しい接続への割り当てを行い，成功したら復帰通知（`SESSION_RESUMED`）を返す
- 復帰したクライアントは準備完了（`READY_FOR_GAME`）を送り直し，現在のプレイヤー一覧・サーバー経過時間・マップ全体の塗り状態を受け取って試合状態を復元する．離席中に Bot が積み上げた塗り面積・個人成績はそのまま引き継がれる
- 「再接続中...」の表示には「タイトルへ戻る」ボタンを置き，回線が戻らない場合でもプレイヤーが自力で抜けられるようにする（[SPEC_04_HUD_UI仕様](SPEC_04_HUD_UI仕様.md) の「再接続中表示」を参照）
- 予約を解決できない場合はサーバーが復帰を拒否し（`RESUME_SESSION_REJECTED`），クライアントはセッションを破棄してタイトル画面へ戻し「試合は終了しました」を表示する
  - 拒否理由は予約が見つからない場合（`expired`）と試合の実体を解決できない場合（`game_ended`）に分かれるが，表示は区別しない
  - 予約の寿命はゲームセッションの寿命と一致するため「予約が見つからない」ことと「試合が終わっている」ことは同値になる．また復帰要求はゲーム画面での再接続でしか送られない

※ Socket.IO の `connectionStateRecovery` は復帰の主機構として採用しない．理由は (1) 接続IDとプレイヤーIDを同一視したアプリ状態までは復元されない (2) 復元は保証されないためフォールバックの実装がどのみち必要になる (3) 導入検討時は意図的な切断を退室として使っていたため，接続状態が復元されると正常系が壊れる（現在は `LEAVE_ROOM` に置き換え済み），の 3 点である．

##### ロビー中の切断 (Disconnection in the Lobby)

ゲーム開始前（ロビー画面）での切断は復帰の対象外とする．サーバーはプレイヤーをルームから退室させるだけで，Bot への置き換えも席の予約も行わない．

- 遷移先: タイトル画面
- 表示: 「接続が切れました，もう一度参加してください」を表示する（「TAP TO START」の状態でも見える位置に置く）
- 通知の消去: 次の入室要求を送信した時点で消す

タイトル画面・リザルト画面での切断は無視する．これらのフェーズではサーバー上のセッションを利用していないためである．

検知は `disconnect` イベントで行い，フェーズの判定は状態遷移（reducer）の内部で行う．

##### 意図的な退室 (Explicit Leave)

ルームから抜けることを明示するために，退室イベント（`LEAVE_ROOM`）を用いる．サーバーは Bot への置き換えを行わずにプレイヤーを退室させ，復帰予約とプレイヤーIDの割り当てを破棄する．ソケットは切断しない．

- ロビー画面の「タイトルへ戻る」
- 「再接続中...」表示の「タイトルへ戻る」
- リザルト受信時（終了した試合の席と予約をサーバーに残さないため）

※ 以前はクライアント自身の意図的な切断・再接続を暗黙の退室として用いていたが，「切断＝離脱」と「切断＝一時的な離席」を区別できないため，明示のイベントに置き換えた．

##### 制約 (Limitations)

- 再接続が間に合わないまま試合が終了した場合は復帰できず，リザルト画面も見られない
- 復帰できるのは「再接続中...」の状態からの自動再接続に限る．ゲーム中にページを再読み込みするとアプリが初期状態から起動するため，元の席へは戻れない

#### アプリ更新の適用 (Applying App Updates)

PWA はキャッシュした古いバンドルを配信し続けるため，放置するとサーバーとの契約がずれ「画面は動くのに参加・操作ができない」状態になる．そこでクライアントは新しい版を検出し，**安全なタイミングでのみ**リロードして適用する．

- Service Worker の登録方式は `prompt` とし，新しい版は待機（waiting）状態に留める．適用のタイミングはアプリ側が制御する
  - ※ 更新検出時に即リロードする方式（`autoUpdate`）では，以下の適用条件を評価する余地がないため採用しない
- 更新チェックの契機: ページ読み込み時に加え，アプリが前面に戻ったとき（`visibilitychange` で `visible` になったとき）
- 適用（リロード）は以下を**すべて**満たすときのみ行う
  - 現在の画面がタイトル画面である
  - タイトルの入力フォームが開いていない（「TAP TO START」を押す前）
  - 接続断の通知・プロトコルバージョン不一致の通知のいずれも表示していない
  - そのセッションでまだ更新によるリロードをしていない（1 セッション 1 回まで）
- 条件を満たさない間は更新を保留し，タイトル画面へ戻った時点で再評価して適用する

適用を除外する理由は以下のとおり．

- ロビー画面・ゲーム画面: リロードするとアプリが初期状態から起動するため，ロビーの参加状態にも試合中の席にも戻れない（「接続断からの復帰」の「制約」を参照）
- リザルト画面: 試合結果はクライアントのメモリ上にしか無いため，リロードすると結果が消える
- 接続断の通知を表示中: 通知が消えてプレイヤーが状況を理解できなくなる（「接続断からの復帰」の表示と衝突する）

※ 条件が揃わないままアプリを終了した場合も，クライアントが 0 になった時点で待機中の Service Worker が繰り上がるため，次回の起動時は新しい版になる．

#### 遅延チャンクの取得失敗からの復旧 (Recovering From Chunk Load Failures)

描画ライブラリ（Pixi.js）は実体を**動的 import で遅延読み込み**するため，ゲーム開始時に初めてチャンクを取りに行く．Service Worker の管理下に入っていないページはこれをネットワークへ直接取りに行くため，配信中に再デプロイされてハッシュ付きの旧チャンクが消えていると 404 になり，ゲームを開始できない．

- 管理外になる主な窓は**初回訪問セッション**である．Service Worker は活性化時に既存タブの制御を引き継ぐ（`clientsClaim`）が，それ以前に読み込まれたページはそのセッションの間ずっと管理外のままになりうる
- クライアントは遅延チャンクの取得失敗を検知したら，更新チェックとリロードを自動で実行する（1 セッション 1 回まで）
- 自動復旧で解消しない場合は，従来どおりゲーム画面に「ゲームを開始できませんでした」を表示する
- 検知はゲーム画面に限らず**アプリ全体**で行う．チャンクの欠落はゲーム開始以外の遅延読み込みでも起こりうる

この復旧は前述の「安全なタイミングでのみ適用する」条件を通さない．条件が抑えるのは**能動的な更新の適用**であり，こちらは**既に壊れたページの事後復旧**であるため位置づけが異なる（「プロトコルバージョンの照合」の自動復旧と同じ扱い）．

※ 復旧の回数制限は更新適用・プロトコル版不一致の復旧とは別に数える．片方の復旧がもう片方の 1 回分を消費してはならない．
　ただし復旧が待機中の更新の適用によって行われた場合は，更新適用のリロードが実際に起きたことになるため，更新適用側の回数も記録される．素のリロードで復旧した場合は記録されない．

※ 復旧のリロードでプレイヤーはタイトル画面へ戻り，参加中のルーム・試合には戻れない（「接続断からの復帰」の「制約」と同じ）．

#### プロトコルバージョンの照合 (Protocol Version Check)

クライアントとサーバーは共有のプロトコル契約バージョン（`PROTOCOL_VERSION`．`packages/shared/src/protocol/protocolVersion.ts`，現在値は `"2"`）を持ち，接続時に照合する．版ずれのクライアントを接続前に弾き，前述の「画面は動くのに操作できない」状態を防ぐ．

- クライアントは接続時のハンドシェイクの `auth` に `protocolVersion` を含めて送信する
- サーバーは接続ミドルウェア（`io.use()`）で厳密に比較し，一致しない場合（未送信を含む）は**接続を拒否する**．拒否した接続はサーバーログに記録する
- クライアントは拒否を検知したら，まず再接続の試行を止めたうえで，更新チェックとリロードを自動で実行する（1 セッション 1 回まで）
- 自動復旧で解消しない場合は，タイトル画面に「アプリの更新が必要です，一度アプリを終了してから開き直してください」を表示する
- `PROTOCOL_VERSION` は client / server 間の互換性が壊れる変更（ペイロード形状の変更・イベント廃止 等）を入れたときに更新する

※ 照合を導入した版をデプロイした直後は，キャッシュ済みの旧クライアントが拒否されるため初回の参加がタイムアウトする（[ENV_10_Renderデプロイ手順](../02_ENV/ENV_10_Renderデプロイ手順.md) の「デプロイ直後の一度きりの劣化」を参照）．

## チーム仕様 (Team Specification)

### チーム構成 (Team Structure)

- チーム数: 4
- チーム名とID:
  - ID 0: 赤チーム
  - ID 1: 青チーム
  - ID 2: 緑チーム
  - ID 3: 黄チーム

### チーム割り当て方式 (Team Assignment Methods)

- ランダム（random）: サーバーが人数バランスを考慮して自動割り当てする
- プレイヤー選択（player_select）: プレイヤーが希望チームを選択する
  - 満員のチームは選択できない
  - 未選択の場合はランダムに割り当てられる

### Bot（AI プレイヤー） (Bot AI Players)

- 目標人数に対して人数が不足する場合，Botが自動的に補充される
- 接続切断したプレイヤーはBotに置き換えられる
  - ゲーム中の切断であれば席が予約され，同じセッショントークンで再接続すると人間の操作へ戻る（「接続断からの復帰」を参照）
